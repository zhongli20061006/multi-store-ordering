# 多门店点单系统 · 设计初稿（v3，待评审）

> 状态：待用户评审。评审通过后，本初稿的结论将合并进各专题真源（project-brief / database-design / architecture / backend-boundary / security-boundary 等），并以本文档为评审依据。

## 一、方向与目标

做一套属于自己的多门店线上点单系统：

- 顾客：微信小程序选门店、看菜单、下单（原型不收款，到店付款）
- 商家：网页后台管理门店、菜单、订单，并作为二期美团/抖音团购券核销入口
- 后端：统一管理数据与规则（价格、状态、权限）
- 当前交付：本地原型，跑通点单闭环；支付、核销均为后续加模块

## 二、数据怎么组织（第 1 步结论）

- 一张门店表；商品、菜单、订单全部带“所属门店”标记。
- 同一个商品在不同门店是独立记录：可不同价、可只在一家上架。
- 管理员与门店的关系放绑定表，决定谁能操作哪个门店。
- 订单明细保存“下单时的名称与价格快照”，改菜单不影响历史订单。
- 菜单策略：每家门店独立维护；不做总部模板（以后可加“从模板复制”，不动地基）。
- 菜单结构支撑：`menu_categories`（门店菜单分类，带门店标记）+ 商品挂 `category_id`，顾客端按分类浏览、商家后台按分类管理；模板复制未来只需复制分类+商品结构。
- 不用“每店一套独立数据库”，统一表 + 门店标记，加门店只是加一行。

## 三、订单生命周期（第 2 步结论）

状态机（只能按箭头走，不能跳步）：

```text
待接单 ──商家接单──▶ 已接单 ──商家完成──▶ 已完成
   │                     │
   └──取消──▶ 已取消      └──取消──▶ 已取消
```

- “做没做”（订单状态 `order_status`）与“付没付”（付款状态 `payment_status`）分开记录。
- 顾客可取消“待接单”订单；商家可取消“待接单/已接单”订单；已接单后顾客不能取消。
- 取消分三类：顾客取消、商家取消-未制作、商家取消-已制作（商家操作时选择）。
- 表结构记录：订单表加 `cancel_reason`（customer_cancel / merchant_cancel_not_made / merchant_cancel_made）与 `cancel_by`（操作人；顾客取消记顾客标识），统计退货、财务对账、二期退款都依赖这两个字段。
- 取消分类的意义：未制作回补库存；已制作不回补（食材已用）。以后接支付时，未制作全额退、已制作按规则部分退/不退，直接接上。
- 取消实现要求：同一数据库事务内完成“锁单 → 校验可取消 → 写状态与取消原因 → 按原因回补库存”；已取消订单重复取消直接返回成功（幂等）。
- 状态只有商家能改；顾客端只读。规则在后端执行。

## 四、库存与防超卖（第 3 步结论）

- 商品可设限库存（限量款），也可不设（不限量）。
- 下单时数据库原子扣减：库存够才扣、扣成功才下单；不足整单拒绝。
- 订单幂等键：连点重复提交只生成一单，不重复扣库存。
- 取消回补规则：未制作的取消 → 回补库存；已制作的取消 → 不回补。
- 原型取消按整单算；以后若需“一单里部分已做”，再细化到明细级。

## 五、账号与权限（第 4 步结论）

- 商家：账号 + 密码登录（加密存储），登录后凭令牌（JWT）访问。
- 权限 = 绑定门店：账号只能看到/操作自己绑定的门店；越权由后端拒绝。
- 不做“老板”角色（以后加账号标记即可）；一个账号可绑多家店。
- 商家以后可接微信登录：把微信号绑定到商家账号，扫码即登录（用户表已留绑定位置）。
- 顾客端不登录：原型用手机号查自己的订单；以后接微信登录再换正式身份。
- 查单隐私（v2/v3）：顾客查单必须同时提供“手机号 + 订单号”；商家端订单列表手机号脱敏（138****0001），详情显示完整号码（用于联系顾客，仅限有该门店权限的账号）。
- 联系策略（v3）：加密通话/隐私号（第三方中转号码，双方互不可见真实号码）作为上线前评估项——需第三方服务、企业资质与费用，原型不接；接支付前后一并评估。

## 六、支付预留与美团/抖音核销（第 5 步结论）

支付（原型不接，只留位置）：

- 订单只记“未付款/已付款”；到店付款由商家标记。
- 新增“支付记录表”：订单、渠道（微信支付 / 支付宝）、金额、状态、回调记录。
- 以后接微信/支付宝：支付回调自动把订单标成已付款；订单结构不用动。

美团/抖音核销（二期）：

- 顾客在美团/抖音购买团购券，到店后店员在系统核销。
- 新增“核销记录表”：平台（美团/抖音）、券码、第三方订单号、核销状态、门店、店员、时间。
- 一张券只能核销一次（防重复核销）。
- 核销入口：商家后台网页（手机浏览器登录即可），支持输入/扫码枪扫券码。
- 二期实施前必须核查平台官方文档、资质、沙箱与接口权限。

## 七、技术栈与目录（第 6 步结论）

| 部分 | 技术 |
| --- | --- |
| 顾客小程序 | 微信原生小程序（开发者工具 + 测试号） |
| 商家后台 | Vue 3 + Element Plus（网页） |
| 后端 | Python FastAPI + SQLAlchemy + SQLite（本地）→ 上线换 PostgreSQL |

SQLite 本地配置：开启 WAL、busy_timeout、连接池大小=1、check_same_thread=False；上线切 PostgreSQL 后按正式连接池配置。

```text
本项目/
├── backend/      后端（业务规则、数据库、接口）
├── admin/        商家后台（网页）
├── miniprogram/  顾客小程序
└── dev-docs/     内部规则与设计文档
```

三端只通过接口对话，统一返回格式；任一端换技术不影响另一端。

商家后台交互：登录后选择“当前门店”（记住上次选择），所有管理操作带 store_id，后端逐请求校验归属；新订单 8 秒轮询提醒，预留 WebSocket 升级。

## 八、明确不做（本阶段非目标）

- 在线支付、微信登录（顾客/商家）
- 美团/抖音核销（二期）
- 外卖配送、会员/积分/营销、库存进销存
- 老板总览角色
- 部署上线（原型本地运行）

## 九、演进预留（只留缝，不实现）

- 支付渠道：微信支付、支付宝（支付记录表按渠道记录）
- 商家微信登录：账号绑定微信号
- 隐私号/加密通话：上线前评估第三方号码隐私服务（资质与费用）
- 老板角色：账号加标记
- 总部菜单模板：以后加“从模板复制”功能
- 店员核销小程序：以后可选开发
- 抖音/支付宝点单小程序客户端：若确认，小程序端需迁移跨端框架，后端接口不受影响

## 十、索引与幂等键

- 唯一索引：`orders.order_no`、`orders.idempotency_key`（客户端生成 UUID）。
- 组合索引：`orders(store_id, order_status, created_at)`、`menu_items(store_id, is_active)`、`menu_categories(store_id)`。
- 幂等键生命周期：原型不做定时清理，上线前再评估（当前量级无必要）。
- 取餐时间（pickup_time）：当前设计无此概念，暂不建字段与索引；二期按需加入。

## 十一、验收口径（原型）

顾客完整下一单成功 + 商家后台接单/取消/完成/标记付款 + 数据落库、金额与状态正确 + 越权与非法输入被拒。具体清单见 acceptance.md。
