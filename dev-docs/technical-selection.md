## 候选组合

### 候选 A（采用）：微信原生小程序 + Vue3/Element Plus 后台 + Python FastAPI + SQLite→PostgreSQL 缝

- 客户端：微信原生小程序（JS），微信开发者工具直接预览，零跨端抽象。
- 商家后台：Vue 3 + TypeScript + Vite + Element Plus。
- 后端：Python 3.11 + FastAPI + SQLAlchemy 2.0 + SQLite（原型）→ 生产可换 PostgreSQL（SQLAlchemy 方言隔离）。
- 拓扑：单进程 monolith，REST JSON API，JWT 管理端鉴权。

适配结论：全部为框架原生能力；目录按模块（stores/menus/orders/auth）组织；无自定义总线、无队列、无微服务。

### 候选 B（拒绝）：uni-app（Vue3）跨端小程序

- 理由：跨端（微信/抖音/支付宝）能力真实存在且成熟；但抖音客户端属 speculative，本阶段引入编译链与框架抽象增加原型复杂度。
- 迁移悬崖：从微信原生迁 uni-app 需重写小程序端；后端 API 不变。
- 触发条件：抖音/支付宝点单客户端成为 confirmed_next 时，重新评估（届时客户端约 6-8 页，重写成本有限）。

### 候选 C（拒绝）：Taro（React）跨端小程序 + React 后台

- 理由：与 B 相同的跨端能力与复杂度问题；且后台若用 React 生态则与常见中文管理端习惯不同，本阶段无收益。
- 触发条件：同上，作为 B 的等价备选。

### 候选 D（拒绝）：后端 NestJS（TypeScript）

- 理由：全 TS 栈统一度高，但用户环境已有 Python/FastAPI 使用经验且本机 Python 3.11 就绪；原型期 FastAPI 自动文档与 Pydantic 校验更轻。
- 触发条件：若团队后续强约束全 TS，可迁移后端（成本中等），当前无证据支持。

### 候选 E（拒绝）：MySQL/PostgreSQL 直接起步

- 理由：原型无并发与数据量压力，SQLite 零安装零运维；SQLAlchemy 方言隔离保留低成本切换路径。
- 触发条件：上线/联调真实多用户时切 PostgreSQL（保留迁移计划）。

## 架构模式轴决策

| 轴 | 选择 | 理由 | 被拒项 |
| --- | --- | --- | --- |
| 部署拓扑 | 单进程 monolith | 一人一产品，无独立部署/扩容需求 | 微服务/Serverless（无驱动） |
| 内部依赖 | 框架原生分层（route→service→model） | FastAPI/ SQLAlchemy 原生结构已满足 | Clean/Hexagonal（过度分层） |
| 领域建模 | 事务脚本/CRUD 服务 | 订单状态机简单，集中到 service 层 | 完整 DDD（规则密度不足） |
| 读写模型 | 统一模型 | 读写形态一致 | CQRS（无驱动） |
| 通信 | 同步调用 | 请求-响应即时完成 | 消息队列（无异步需求） |
| 客户端 API | 共享 REST API | 两个客户端行为/安全需求一致 | BFF（无差异化需求） |
| 扩展性 | 内置模块 | 团队自有全部能力 | 插件架构（无第三方扩展需求） |
| 组织 | 产品应用 | 单产品单团队 | 中台（无证据） |

## 迁移悬崖与再评估触发

- 小程序端跨平台：若抖音点单客户端确认，客户端重写（约 6-8 页），后端不受影响。触发：用户确认抖音点单需求。
- 数据库：SQLite → PostgreSQL，SQLAlchemy 方言切换 + 数据迁移，成本低。触发：真实多用户联调或上线。
- 支付/登录：订单支付状态、用户 openid 字段已预留；接微信支付时新增支付单与回调，不改核心订单模型。触发：阶段二启动。
- 核销：订单模型不动，新增核销记录表与第三方适配模块。触发：阶段三启动。
